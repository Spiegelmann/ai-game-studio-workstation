# POLICY-005 — Policy Decision Explainability & Evaluation Trace

## Objective

Extend the policy domain with a deterministic, immutable explanation/evaluation trace for policy decisions.

The purpose of this task is to make policy decisions **auditable and explainable inside the domain model** without introducing persistence, logging infrastructure, authorization, execution, orchestration, external providers, or security enforcement.

After POLICY-005, a caller evaluating an action should be able to understand **why** the evaluator produced `Allow`, `Deny`, or `Escalate`, including the relevant capabilities, provenance/trust state, scope relationship, rule outcome, and precedence that influenced the final decision.

This is a **domain-level decision explanation mechanism**, not an operational logging system.

---

# 1. Scope

Implement only the following:

1. Immutable policy evaluation evidence/trace primitives.
2. Deterministic representation of evaluation steps.
3. A deterministic explanation attached to the policy decision/evaluation result.
4. Explicit representation of:

   * evaluated action
   * applicable rules
   * capability availability
   * capability provenance/trust
   * scope relationship
   * allow/deny/escalate outcomes
   * final precedence
   * reasons for skipped/inapplicable candidates where useful
5. Tests proving determinism, immutability, and consistency with existing POLICY-001 through POLICY-004 semantics.
6. Documentation describing the new explanation model and its boundaries.

Do **not** implement:

* authorization
* authentication
* identity
* user/agent permissions
* filesystem or OS enforcement
* resource discovery
* tool execution
* orchestration
* approvals
* persistence
* SQLite changes
* event publishing
* external logging
* telemetry infrastructure
* LLM-generated explanations
* natural-language reasoning generated by an AI
* MCP/tool integration
* policy configuration loading
* capability registration infrastructure beyond what already exists
* game-specific policy
* scope hierarchy
* scope-independent actions
* policy caching
* distributed coordination

The explanation must be produced entirely from deterministic domain data already available to the evaluator.

---

# 2. Architectural Intent

The policy system currently has the following conceptual progression:

```text
POLICY-001
Decision + deterministic policy boundaries
        ↓
POLICY-002
Capabilities + rules + deterministic evaluation
        ↓
POLICY-003
Capability provenance + trust
        ↓
POLICY-004
Capability scope + boundary constraints
        ↓
POLICY-005
Explainable deterministic evaluation trace
        ↓
Future
Authorization / Security / Orchestration / Execution
```

POLICY-005 must preserve this separation.

The Core policy model must remain:

* deterministic
* immutable where practical
* provider-independent
* free of infrastructure dependencies
* free of I/O
* free of logging frameworks
* free of persistence concerns
* free of execution concerns

The evaluator must remain the source of truth.

Do not create a second independent policy engine merely to generate explanations.

The explanation must be derived from the **same evaluation process that produces the final decision**.

---

# 3. Core Design Principle

A policy decision without an explanation should no longer require the caller to reconstruct the evaluator's reasoning manually.

However, avoid creating a verbose "debug dump".

The trace should represent **structured domain facts**, not arbitrary diagnostic strings.

Prefer strongly typed values such as:

* candidate rule
* candidate capability
* provenance/trust status
* scope comparison
* candidate outcome
* reason code
* final precedence

over:

```text
"Well, this capability probably failed because..."
```

Do not make the policy system dependent on natural-language messages.

Structured reason codes remain authoritative.

Human-readable formatting, if provided, must be a projection of the structured trace rather than the source of truth.

---

# 4. Introduce an Immutable Evaluation Trace Model

Create a small domain model for policy evaluation traces.

Names may differ if existing conventions suggest better names, but the conceptual model must remain equivalent.

For example:

```text
PolicyEvaluationTrace
PolicyEvaluationStep
PolicyEvaluationCandidate
PolicyEvaluationOutcome
```

Do not blindly create all four types if fewer types provide a cleaner model.

The resulting API should allow a caller to inspect:

```text
Action
Candidates evaluated
Candidate results
Reasons
Final decision
```

without needing to know evaluator internals.

---

# 5. Trace Step Requirements

Each meaningful evaluation step should expose structured information sufficient to answer:

### What was evaluated?

Examples:

* action
* capability
* rule
* registration

### What information was available?

Examples:

* capability present/missing
* provenance known/unknown
* trust trusted/untrusted/unknown
* scope known/matching/mismatching/unknown

### What happened?

Examples:

* applicable
* not applicable
* allowed
* denied
* escalated
* skipped

### Why?

Use the existing structured policy reason model wherever possible.

Do not replace existing reason codes with free-form strings.

If a new reason code is required, introduce it deliberately and document it.

---

# 6. Preserve Existing Decision Semantics

POLICY-005 must not change policy behavior merely to make explanations easier.

All existing semantics remain authoritative.

In particular:

## Final precedence

```text
Deny > Escalate > Allow
```

An explanation must make this precedence observable.

For example, if:

```text
Candidate A → Allow
Candidate B → Escalate
Candidate C → Deny
```

the final result must remain:

```text
Deny
```

and the trace must make it possible to determine that the deny candidate outranked the others.

Similarly:

```text
Allow
Allow
```

must remain:

```text
Allow
```

and:

```text
Allow
Escalate
```

must remain:

```text
Escalate
```

Do not introduce a new precedence system.

---

# 7. Explain Existing POLICY-003 Provenance Semantics

The trace must distinguish at minimum:

* trusted provenance
* unknown provenance
* untrusted provenance
* missing provenance where applicable

The evaluator must preserve the existing behavior:

```text
Trusted + otherwise valid
    → may Allow

Unknown provenance
    → Escalate

Untrusted provenance
    → Escalate

Explicit Deny
    → Deny remains strongest
```

The explanation should identify the provenance/trust outcome that caused the candidate to allow, deny, or escalate.

Do not expose implementation-specific security assumptions that do not exist in the current domain.

---

# 8. Explain Existing POLICY-004 Scope Semantics

The trace must represent the existing tri-state scope relationship:

```text
Match
NoMatch
Unknown
```

The evaluator must continue to behave as currently implemented.

Examples:

```text
Trusted + Match
    → candidate can Allow

Trusted + NoMatch
    → candidate Deny / excluded according to current evaluator semantics

Trusted + Unknown
    → Escalate

Unknown provenance + Match
    → Escalate
```

Do not change the current scope semantics.

Do not introduce scope hierarchy.

Do not introduce implicit wildcard matching.

Do not interpret missing scope as global.

---

# 9. Explain Capability and Rule Selection

The trace should allow a caller to understand why a capability/rule was considered applicable or not.

At minimum, distinguish:

```text
Applicable
Not applicable
Missing capability
Unsupported action
Explicit deny
```

Preserve existing POLICY-002 action mappings.

Do not add new action mappings as part of this task.

Do not make the evaluator dynamically infer arbitrary mappings.

---

# 10. Determinism

This is a critical requirement.

Given the same:

```text
PolicyAction
PolicyContext
PolicyRules
PolicyCapabilityRegistrations
```

the evaluator must produce:

1. the same final decision
2. the same structured reason(s)
3. the same trace content
4. the same trace ordering

Do not depend on:

* dictionary iteration order
* hash ordering
* timestamps
* GUID generation
* machine state
* filesystem state
* environment variables
* thread scheduling

unless an existing immutable domain identifier is already part of the input.

If collections are involved, explicitly establish deterministic ordering.

Document the ordering rule.

---

# 11. Immutability

The trace must be immutable after creation.

Callers must not be able to mutate the evaluator's internal collections after evaluation.

Avoid exposing mutable:

```csharp
List<T>
Dictionary<TKey, TValue>
ICollection<T>
```

where callers could mutate the underlying evaluation state.

Prefer:

```csharp
IReadOnlyList<T>
IReadOnlyCollection<T>
ImmutableArray<T>
```

or equivalent existing project conventions.

If constructors accept collections, defensively copy them.

Add tests proving that modifying an input collection after evaluation does not mutate the resulting trace.

---

# 12. Do Not Leak Internal Mutable State

The evaluator should not return references to mutable internal collections.

For example, this is undesirable:

```csharp
trace.Steps.Add(...)
```

The consumer should receive an immutable/read-only representation.

Likewise, do not expose internal evaluator state directly.

---

# 13. Decision Result Integration

Integrate the trace into the existing policy evaluation result rather than introducing a parallel evaluation API.

If the current result type is conceptually:

```text
PolicyDecision
```

extend it so that the decision can expose its structured evaluation trace.

For example:

```text
Decision
Reasons
Trace
```

The exact API should follow the existing codebase conventions.

Avoid breaking existing callers unnecessarily.

If backward compatibility requires a constructor or factory overload, add one rather than rewriting unrelated code.

---

# 14. Final Decision Explanation

The final trace must make the relationship between:

```text
candidate outcomes
        ↓
precedence
        ↓
final decision
```

explicit.

For example, a consumer should be able to determine:

```text
Final Decision: Escalate

Candidates:
- workspace.write / trusted / matching scope → Allow
- workspace.write / unknown provenance → Escalate

Final precedence:
Escalate outranks Allow
```

The representation should remain structured.

Do not hard-code English sentences as the only explanation mechanism.

---

# 15. Reason Codes

Reuse existing reason codes wherever possible.

Do not create duplicate reasons simply because the trace now exists.

If a candidate needs to record a result without introducing a new final decision reason, consider representing the candidate outcome separately from the final decision reason.

For example:

```text
Candidate outcome:
  ScopeNoMatch

Final decision:
  Deny

Final reason:
  capability.scope.denied
```

The exact design should follow the existing policy model.

---

# 16. Human-Readable Explanation

If the current architecture makes this useful, introduce a deterministic formatter/projector for the structured trace.

However:

* it must be optional
* it must not become the source of truth
* it must not use an LLM
* it must not perform I/O
* it must not introduce localization infrastructure
* it must not replace structured reason codes

If a formatter adds unnecessary complexity, do not add one.

A structured trace is the primary acceptance criterion.

# 17. Testing Requirements

Add focused tests for at least the following.

## Basic trace creation

Verify:

* evaluation produces a trace
* trace contains the evaluated action
* trace contains meaningful evaluation steps
* final decision is represented consistently

## Allow

Test:

```text
trusted capability
matching scope
applicable rule
no deny
```

Expected:

```text
Allow
```

Trace must identify the successful candidate.

---

## Deny

Test an explicit deny.

Expected:

```text
Deny
```

Trace must identify the deny outcome and corresponding reason.

---

## Escalate

Test unknown provenance.

Expected:

```text
Escalate
```

Trace must identify the unknown provenance/trust state.

---

## Scope mismatch

Test known scope mismatch.

Expected:

```text
Deny
```

according to current POLICY-004 semantics.

Trace must identify:

```text
scope relationship = NoMatch
```

---

## Unknown scope relationship

Test unknown scope information.

Expected:

```text
Escalate
```

Trace must distinguish `Unknown` from `NoMatch`.

---

## Precedence

Explicitly test:

```text
Allow + Escalate → Escalate
Allow + Deny → Deny
Escalate + Deny → Deny
Allow + Allow → Allow
```

The trace must make the winning outcome identifiable.

---

## Multiple registrations

Test multiple registrations for the same capability.

Verify:

* each relevant registration can be represented
* deterministic ordering is preserved
* a matching trusted registration can produce Allow
* an unrelated mismatch does not incorrectly override a valid match
* stronger Deny/Escalate semantics remain consistent with the existing evaluator

Do not invent new semantics merely for the trace.

---

## Determinism

Run equivalent evaluations repeatedly.

Verify:

```text
decision == decision
reasons == reasons
trace == trace
ordering == ordering
```

Do not compare object references; compare structural values.

---

## Immutability

Verify that:

* modifying source collections after evaluation does not change the trace
* callers cannot mutate the trace
* nested collections are also protected

---

## No side effects

Verify the evaluator:

* performs no I/O
* does not persist anything
* does not write logs
* does not access environment state

Follow the existing architecture tests where appropriate.
